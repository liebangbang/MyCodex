# MyCodex 稳定性需求文档

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 编写日期 | 2026-08-12 |
| 适用范围 | MyCodex 桌面应用（macOS · pywebview + Python 后端 + JS 前端） |
| 目标 | 保障数据不丢不串、崩溃可自愈可诊断、危险操作有防护、长时运行不劣化 |
| 说明 | 服务器端（猎帮帮系统）稳定性已有独立方案（systemd 守护 + 定时监控），不在本文档范围 |

---

## 1. 背景与现状

MyCodex 是本地编码代理桌面应用：直接读写用户机器上的文件、执行终端命令、接入 DeepSeek（文本）与千问 VL（视觉）。因直接操作真实文件与命令，稳定性是可用性的第一前提。

**当前已具备的稳定性能力：**

| 模块 | 现状 |
|---|---|
| 危险命令确认 | ✅ 正则匹配 rm -rf / sudo / git reset --hard 等，弹窗二次确认 |
| 输出/预览截断 | ✅ 命令输出 40k、预览 60k 上限 |
| 会话存档 | ✅ 每轮结束落盘 JSON，启动自动恢复上次任务 |
| 线程隔离 | ✅ 已修复"发送中切换任务导致串数据"（上下文快照 + 固定写回） |
| 前端异常捕获 | ✅ 全局 error 监听 + 启动 bootstrap 重试 |
| 后端日志 | ⚠️ 仅有 startup.log 简单文本 |

**仍存在的稳定性缺口（本文档要解决的问题）：**

1. 会话文件损坏无自愈（JSON 损坏即丢失/报错）
2. 后台线程仍缺系统性并发保护（写锁、增量保存）
3. API 调用无重试，断网/超时会话丢失
4. 文件操作无安全边界（可改任意路径）
5. 无结构化日志与诊断包
6. 资源占用无监控（大文件、长会话）
7. 多窗口/多实例无隔离与互斥

## 3. 详细需求

### R-01 会话数据一致性（防串防丢）· P0

**问题**：agent 在后台线程运行，操作共享全局状态；任何写竞争都可能把 A 任务的对话写入 B 任务，或丢失未保存的轮次。

**需求**：
- 所有后台 agent 线程使用**任务局部上下文**（history / transcript / artifacts 快照），与全局状态解耦
- 会话写入统一走**原子写**（tmp 文件 + rename），并加**文件级锁**防并发写
- 提供统一的 `_save_ctx(ctx)`：无论用户当前在哪个任务，回复固定写回发起时的任务文件；仅当用户未切换时才同步内存
- 发送中切换 / 新建 / 删除任务的边界行为明确：允许切换查看，但禁止污染

**验收标准**：
1. 在任务 A 发送后立即切到任务 B，A 的完整回复落在 A.json，B 无任何 A 的痕迹
2. 两个线程同时写不同任务，双方文件均完整有效
3. kill -9 强杀进程，已保存轮次不损坏、不串

**状态**：✅ 核心已修复（上下文快照 + 固定写回）；⬜ 原子写锁、并发写测试待补

---

### R-02 会话文件损坏自愈 · P0

**问题**：会话 JSON 损坏（磁盘满、写中断、手动改坏）时，`json.loads` 直接失败，任务打不开甚至列表报错。

**需求**：
- 读取失败时：自动把损坏文件备份为 `<name>.json.bak-<ts>`，重建空会话，并向前端提示"上次会话已损坏，已备份恢复"
- 提供"从备份恢复"入口（列表/任务打开失败时，检测 .bak 文件并给出恢复选项）
- 残留 `.tmp` 文件启动时自动清理

**验收标准**：
1. 人为把某会话 JSON 改成非法内容，应用能正常启动，该任务显示为"已恢复的空任务"，损坏文件有备份
2. 备份文件可手动恢复内容

---

### R-03 文件操作安全边界 · P0

**问题**：AI 可读写任意路径（包括 ~/.ssh、业务机密目录），误操作不可逆。

**需求**：
- 新增**工作目录白名单**：默认只允许 AI 读写"当前任务工作目录"内文件；越权路径需用户确认
- 工作目录外操作（如 `/etc`、`~/Desktop/合同`）默认拒绝并明确提示
- 危险命令确认升级：增加"越权路径写入/删除"识别（如 `write_file` 目标在工作目录外时，前端弹确认）
- 提供"宽松模式"开关（高级用户可关闭白名单）

**验收标准**：
1. 在任务目录内正常读写，无打扰
2. 尝试 write/delete 工作目录外文件，被拦截并提示
3. 开启宽松模式后行为恢复原状

---

### R-04 网络容错与重试 · P1

**问题**：API 单次请求 600s 超时，失败即整轮结束；断网/波动时任务中断、上下文已产生却未落盘。

**需求**：
- 对**可安全重试**的请求（非工具执行的纯对话轮）做自动重试：指数退避（1s / 2s / 4s / 8s），最多 4 次
- 工具执行后的重试**必须幂等**：同一工具调用失败时不自动重复（避免重复写文件/重复执行命令），改为提示用户重发
- 断网时前端明确显示"网络异常，等待重连"，恢复后继续
- 超时可配置（默认 600s）

**验收标准**：
1. 模拟网络抖动（请求中断 2 次），对话自动恢复不丢消息
2. `write_file` 因网络中断失败后，不会被自动重复执行

---

### R-05 崩溃恢复与增量保存 · P1

**问题**：当前只在每轮结束时保存；生成中强杀进程，整轮内容丢失。

**需求**：
- 改为**增量保存**：每轮结束后、以及每次工具调用完成后都落盘（依赖 R-01 的原子写）
- 启动时若检测到上次异常退出（存在未清理的 `.running` 标记），提示"上次任务未正常完成，已恢复到最近完整轮"
- 记录每轮完成的进度索引，重启后可恢复到最近完整轮，不重复执行已完成的工具调用

**验收标准**：
1. 生成中强杀，重启后恢复到最近完整轮，已完成的工具结果还在
2. 不重复执行已完成的写文件/命令

---

### R-06 资源占用控制 · P1

**问题**：大文件（100MB）、超长会话、超大命令输出会拖慢甚至卡死界面。

**需求**：
- 命令执行超时**可配置**（默认 120s），并提供"超时后是否保留部分输出"
- 大文件预览虚拟化：超过阈值只读前 N KB + 尾部 N KB，标注文件大小
- 长会话（如 >500 轮）提示"可压缩历史"，提供一键摘要压缩（依赖模型）
- 记录会话 JSON 体积，>5MB 提示归档

**验收标准**：
1. 打开 100MB 文本文件，预览区不卡死，显示前后片段 + 总大小
2. 连续运行 10 小时，内存占用平稳无泄漏趋势

---

### R-07 结构化日志与诊断包 · P1

**问题**：startup.log 简单文本，出问题难以定位；无集中诊断手段。

**需求**：
- 结构化日志：`时间 | 级别 | 模块 | 事件`，落盘 `~/.config/mycode/logs/mycodex.log`
- 按大小轮转（保留最近 3 份）
- 日志级别可配置（debug / info / warn / error）
- **一键导出诊断包**：菜单/命令触发，打包 { 日志 + 会话文件列表 + 配置文件脱敏 + 系统版本 } 为 zip

**验收标准**：
1. 触发一次错误，日志中能定位到模块与调用栈
2. 诊断包不含 API Key（脱敏确认）

---

### R-08 全局异常兜底 · P1

**问题**：后端线程异常、JS 异常可能白屏或静默失败。

**需求**：
- 后端：agent 线程最外层统一 try/except，异常 → 写日志 + 前端提示"出错了，详情见日志"，不静默
- 前端：保留全局 error 监听，JS 异常显示红色横幅（含文件/行号），并上报诊断包入口
- 工具调用异常（如编码错误）返回明确错误而非整轮崩溃

**验收标准**：
1. 人为制造后端异常（如让工具抛错），界面不白屏、有提示、日志有记录
2. JS 运行时错误可见并可导出

---

### R-09 多窗口/多实例隔离 · P2

**问题**：当前单窗口；未来多窗口时，共享同一会话文件，可能写冲突。

**需求**：
- 多实例共享会话数据，但写入互斥（文件锁 + 最后写入者校验）
- 打开同一任务的两个窗口，A 窗口保存后 B 窗口检测到文件变更，提示刷新
- 启动时清理残留 `.tmp`

**验收标准**：
1. 两个窗口同时操作不同任务，互不干扰
2. 两个窗口打开同一任务，后写者不覆盖先写者的未保存内容（或明确提示冲突）

---

### R-10 文件操作审计 · P2

**问题**：无法回溯"AI 到底改过哪些文件、执行过哪些命令"。

**需求**：
- 每次 write_file / edit_file / run_command 记录审计条目：`时间 | 任务 | 文件/命令 | 结果`
- 落盘 `~/.config/mycode/audit.log`（追加式）
- 任务详情可查看"该任务的文件变更历史"

**验收标准**：
1. 任意任务可回溯其修改过的全部文件与执行过的命令
2. 审计日志不可被 AI 工具自身修改（只追加）

---

### R-11 启动自检 · P2

**问题**：配置缺失、依赖损坏、磁盘满时启动无提示，用户困惑。

**需求**：
- 启动自检项：API Key 配置、必要依赖（pywebview 等）、会话目录可写、磁盘剩余空间、config.json 合法性
- 异常项启动横幅提示，并给出修复指引（如"请设置 api_key：…"）
- 顶栏/关于显示版本号

**验收标准**：
1. 故意删除 api_key，启动后顶部明确提示配置方法
2. 会话目录不可写时，启动即有警告

## 5. 整体验收标准（发布门槛）

1. **数据安全**：任何操作序列下，任务间数据零串扰；进程强杀后已保存轮次完好
2. **故障可恢复**：断网、API 失败、会话损坏、进程崩溃四类故障均可恢复且不丢已提交内容
3. **安全边界**：默认工作目录白名单生效，越权操作必须显式确认
4. **可诊断**：一次故障从日志/诊断包可定位根因，无需用户描述
5. **资源稳定**：连续 10 小时运行，内存与磁盘无异常增长

## 6. 风险与权衡

| 风险 | 权衡与对策 |
|---|---|
| 工作目录白名单限制正常操作 | 提供宽松模式开关；只拦截"确认危险"的越权写/删 |
| 自动重试可能重复副作用 | 只对纯对话轮重试；工具调用一律不自动重试 |
| 增量保存增加 IO | 保存节流（每轮最多 1 次 + 工具链结束时 1 次），文件小且原子 |
| 多窗口互斥复杂 | 先行单窗口 + 文件变更检测，多窗口完整支持后置 |
| 日志含敏感路径 | 诊断包导出时对用户名、路径、Key 脱敏 |
